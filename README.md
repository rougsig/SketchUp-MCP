# Local SketchUp MCP

Локальный MCP-сервер и Ruby-расширение для настольного SketchUp на Mac и Windows.
Целевая версия пользователя: SketchUp 26.2.242. Встроенных зависимостей Python
достаточно; скачивать Python-пакеты не нужно. Требуется Python 3.9 или новее.

```text
MCP-клиент → Python (stdio) → локальные JSON-файлы → Ruby-расширение → открытая модель
```

Оба процесса должны работать на одном компьютере под одной учётной записью.
Расширение обращается к модели через SketchUp Ruby API. Сохранённый `.skp` не
разбирается напрямую: доступны и несохранённые изменения открытой модели.
Сетевых портов, облачного сервера и ключей API у этого проекта нет. Подключённый
ИИ-клиент может отправлять полученные данные модели своему провайдеру.

## Установка на Mac

1. Помести проект в `/Users/st/projects/SketchUp-MCP`.
2. В SketchUp открой **Extension Manager → Install Extension** и выбери
   `dist/sketch-up-mcp.rbz`. Названия пунктов зависят от языка интерфейса.
3. Открой **Extensions → Local SketchUp MCP → Start bridge**.
4. Добавь сервер в настройки локальных MCP-серверов своего ИИ-клиента.
   Образец для клиентов с форматом `mcpServers` находится в `mcp-config.mac.json`:

   ```json
   {
     "mcpServers": {
       "sketchup": {
         "command": "python3",
         "args": ["/Users/st/projects/SketchUp-MCP/server/server.py"]
       }
     }
   }
   ```

   Если клиент не находит Python, выполни в терминале `which python3` и используй
   полученный абсолютный путь в `command`. Если клиент использует другой формат
   настройки, укажи тот же исполняемый файл и аргумент средствами этого клиента.
   Не заменяй весь существующий конфиг: добавь `sketchup` к имеющимся серверам.
5. Перезапусти MCP-подключение в клиенте. Он запускает Python-сервер сам.

`mcp-config.mac.json` — образец настройки, его наличие в папке само по себе
не подключает сервер. И расширение, и MCP-клиент требуют однократной настройки.

## Установка на Windows

1. Скопируй папку проекта на Windows, например в
   `C:\Users\YOUR_USER\projects\SketchUp-MCP`.
2. Проверь наличие Python 3.9+: `python --version`. Если его нет, установи Python.
3. Установи тот же `dist/sketch-up-mcp.rbz` через **Extension Manager** и включи
   **Extensions → Local SketchUp MCP → Start bridge**.
4. Используй `mcp-config.windows.json`, заменив `YOUR_USER` на свой путь.
   При необходимости укажи полный путь к `python.exe` в `command`.
5. Перезапусти MCP-подключение клиента.

На каждой машине работает своё локальное подключение. Модели между машинами
этот проект не синхронизирует. Расширение стартует вручную после запуска SketchUp;
его можно остановить через **Stop bridge**.

## Обновление до 0.3.0

Версия содержит **41 инструмент**. Добавлены `create_sphere`, `create_cone`,
`export_scene` и `eval_ruby`; сфера и конус также доступны в `build_assembly`.
Исходники, RBZ и скрипт установки подготовлены; само открытое приложение нужно
обновить один раз из Ruby Console. В этой рабочей папке команда такая:

```ruby
load '/Users/st/projects/SketchUp-MCP/activate.rb'
```

Скрипт остановит старый bridge, скопирует расширение в папку Plugins,
загрузит новую версию и запустит bridge. Затем выполнит нативный smoke test
с откатом тестовой операции и запишет результат в `dist/native-smoke-result.json`.
Выйди из редактирования компонентов перед запуском.
Затем **перезапусти MCP-подключение в клиенте**, чтобы он перечитал список инструментов.
В новых сессиях обновлённый RBZ можно установить обычным Extension Manager.

Импорт, запуск Ruby-файлов и экспорт работают внутри настроенных папок. `activate.rb`
добавляет папку проекта `SketchUp-MCP`. Для других папок используется
**Extensions → Local SketchUp MCP → Add automation folder**; после перезапуска
SketchUp этот пункт доступен в обновлённом меню. Настройки хранятся в
`~/.sketch-up-mcp/automation-folders.json`. Символические ссылки проверяются
по реальному пути. Альтернатива: `SKETCHUP_MCP_ALLOWED_ROOTS` со списком путей,
разделённым системным разделителем (`:` на Mac, `;` на Windows).

## Возможности

### Генерация artifacts и технический рендер

Исходники пяти моделей находятся в `artifacts/<model>/build_model.py` и,
для составных корпусов, `layout.py`. Генерация геометрии и режим `draft`
требуют только Python 3.9+. Рендер высокого качества использует NumPy:
`python3 -m pip install -r requirements-render.txt`.

```sh
# Все модели, варианты и технические PNG высокого качества:
python3 scripts/generate_artifacts.py
# Прежние PNG/SVG без NumPy:
python3 scripts/generate_artifacts.py --quality draft
# Только DAE и JSON:
python3 scripts/generate_artifacts.py --geometry-only
# Один модуль или вариант:
python3 scripts/generate_artifacts.py detergent-cabinet
python3 scripts/generate_artifacts.py laundry-sink --variant open
# Рендер готового DAE без генерации:
python3 scripts/render_artifacts.py artifacts/laundry-sink/cache/laundry-sink-open.dae --output /tmp/sink.png
python3 scripts/render_artifacts.py artifacts --width 600 --height 600
```

Все генерируемые DAE, JSON, PNG, SVG и SKP находятся в `artifacts/<model>/cache/`.
Папки `cache/` исключены из Git и сборочного архива; их можно восстановить генератором.
Перед нативной сборкой запускай генерацию геометрии.

Отдельный рендер пишет `cache/<dae-stem>-render.png`; доступны `--yaw`, `--elevation`,
`--width`, `--height`, `--hide-zones`, `--samples 1|2|3`.
По умолчанию `--quality high --style technical`: сглаживание, мягкие тени,
тонкие контуры деталей, светлый фон и прозрачные красные зоны с границами.
`--style studio` даёт более контрастное освещение; `--quality draft` использует
прежний рендер стандартной библиотеки. Поддерживаются треугольные
DAE с цветами материалов, единицами COLLADA, осями X/Y/Z_UP,
вложенными трансформациями и локальными экземплярами узлов;
неподдерживаемые типы геометрии отклоняются. `--hide-zones` исключает прозрачную геометрию.

У стойки вариант `open` изменяет только PNG-превью, DAE остаётся закрытым.
JSON раковины и шкафа средств описывает закрытую модель и данные вариантов.

Для редактируемых компонентов используй `build_assembly` из JSON. DAE-импорт
объединяет детали в сетку и подходит для просмотра. В нативной сборке корпус,
дверцы, ящики, отдельные детали и зоны доступны в Outliner; отдельную деталь
можно скрыть стандартной командой SketchUp **Hide**.

Панель **Артефакты MCP** содержит кнопку **Дверцы и ящики — перетаскивание**.
Та же команда находится в **Extensions**. Включи инструмент, зажми дверцу,
её ручку или фасад ящика и потяни мышью. Отпускание фиксирует любое промежуточное
положение; повторное перетаскивание продолжает движение от него.
Дверцы вращаются вокруг петли, ящики движутся вдоль направляющих в пределах
заданного хода. Текущее смещение или угол отображается в строке состояния.
**Esc** отменяет незавершённое движение и выключает инструмент. Это управление
нашего Ruby-расширения; компоненты не требуют Dynamic Components.
Каждое перетаскивание — один Undo. Пока мышь зажата, изменения через MCP блокируются.
Инструмент хранит точное закрытое положение и применяет заданное движение
относительно него, без накопления поворотов и смещений.

В контекстном меню компонента **Артефакт MCP** доступны **Открыть / закрыть**,
**Показать / скрыть зоны** и, у шкафа средств, **Снять / вернуть боковину**.
При выборе целого модуля открываются все его подвижные части; при выборе
отдельной дверцы или ящика — только она. Команды также доступны через
**Extensions → Артефакты MCP** и выходят из режима редактирования компонента.
В JSON группы дверей задаются через `doors` с `hinge_mm`, `angle_degrees`
и необязательной `rotation_axis`; ящики — через `drawers` с `anchor_mm`
и `travel_mm` (по умолчанию 400 мм). `motions` задаёт движения остальных групп.
Это условные положения эскиза, не расчёт реального хода выбранной фурнитуры.

У машин ручка выступает на 13 мм перед ободом: физический размер теперь
600 × 613 × 850 мм. Красные зоны стойки отстоят от панелей на 0,5 мм для
отображения без совпадающих поверхностей; номинальные зазоры не меняются.
DAE-импорт через MCP окрашивает обратную сторону, если она не имела материала.

Навыки для этого процесса хранятся в `skills/sketchup-generate-artifacts`
и `skills/sketchup-render-artifacts`. Их можно установить в каталог навыков Codex.

Прежние команды `get_model`, `list_entities`, `get_selection`, `get_view`,
`create_box`, `move_entities`, `resize_entity`, `set_material` сохранены.
`move_entities`, `resize_entity` и `set_material` по-прежнему работают в текущем
контексте. Для вложенных объектов без ручного открытия используй новые команды.

Длины — миллиметры; X = ширина, Y = глубина, Z = высота. Массив `path`, например
`[123, 456]`, — последовательность persistent ID от корня модели до выбранного
вложенного компонента. Он различает один и тот же компонент в разных экземплярах.
`world_transform_mm` — матрица SketchUp с переводом элементов переноса в миллиметры.
Остальные элементы матрицы безразмерные; порядок столбцов соответствует SketchUp.

Перед вложенной правкой общие определения родителей делаются независимыми.
Это может изменить ID потомков: используй обновлённый `path` из результата.
Внутри `batch_edit` такие пути переназначаются автоматически. Новые операции
изменения запускаются из корневого контекста; входить внутрь компонентов не нужно.

`build_assembly` принимает `assembly` либо `json_path`. Поддерживаются файлы
`artifacts/*/cache/model-primitives.json`, уже созданные для постирочной. В inline JSON
`groups` — массив объектов с `key`, `name`, необязательными `parent`, `anchor_mm`,
`component`, `role`, `tag`; `materials` — массив `key/name/rgb/opacity`; `shapes` —
массив примитивов. Все размеры примитивов заданы в осях родителя своей группы.
`key` на корне — идентификатор модуля, `replace:true` заменяет его одной операцией,
сохраняя положение, поворот и тег. Импортированные объекты можно двигать и измерять;
параметрически перестраиваются только корпуса, созданные `create_furniture`.
Полные модели из других генераторов обновляются через `build_assembly` с новым JSON.
`resize_entity` растягивает все детали, поэтому не подходит для сохранения толщины панелей.

Красные зоны не являются корпусом: `measure_objects` по умолчанию исключает
служебные группы `Zones/Access/Clearances/Service` и плоские примитивы `rectangle`.
`include_zones:true` измеряет общий габарит вместе с ними. Ручки и смеситель входят
в физические габариты. Для габарита одного корпуса измеряй его группу `Frame`.
Скрытые варианты сцен следует измерять по нужным явным путям.

`check_collisions` проверяет реальные параллелепипеды методом разделяющих осей
(SAT), включая повёрнутые и масштабированные коробки. Коробка подтверждается
по метке примитива и текущей геометрии (6 граней, 12 рёбер, 8 углов).
Для других форм возвращается `possible_bounds_overlap`: это предварительная
проверка, а не доказательство пересечения или минимального расстояния поверхностей.
`check_motion` проверяет заданное число промежуточных положений, не изменяя модель;
столкновение между выборками всё ещё возможно. Проходы и доступ к сифону можно
проверять отдельными контрольными объёмами. Полноценного расчёта прочности нет.

Обычная сцена SketchUp сохраняет камеру и видимость, но не трансформации объектов.
`create_scene_variants` создаёт независимые варианты сборки на одном месте,
применяет перемещения/повороты и переключает их тегами. Пути деталей внутри
описания варианта задаются относительно исходной сборки (без ID корня).

Все новые команды записи требуют уникального `operation_id`. Повтор с тем же ID
и теми же аргументами возвращает прошлый результат. Изменённые аргументы с тем же
ID отклоняются. Журнал хранится в каталоге `operations` внутри папки bridge.
После таймаута используй `get_operation_status`. Состояние `running` после сбоя
не разрешает повторное исполнение: сначала нужно проверить модель.
Журнал привязан к сессии SketchUp и модели. Undo в интерфейсе не отменяет запись
журнала; для следующего намеренного изменения используй новый ID.

Каждая обычная новая правка — одна операция Undo с `abort_operation` при ошибке.
`batch_edit` поддерживает трансформации, свойства, покраску, удаление и подписи;
создание полной сборки также само по себе атомарно. Файловое сохранение не является
операцией Undo; экспорт также не оборачивается в Undo. `run_ruby_script` исполняет точные байты, проверенные SHA256, и
полагается на транзакции самого генератора; при исключении возможны частичные
правки, что явно отражается в журнале. Это полноценный Ruby внутри SketchUp.

Готовый пример `examples/assemble_laundry.rb` собирает все пять наших модулей,
создаёт сцену и размер ряда, проверяет ширину **1726 мм** при доступных **1750 мм**.
Он ставит ряд за границами текущей модели; при повторе обновляет модули по ключам.
Его можно запускать через `run_ruby_script` после чтения файла и вычисления SHA256.

## Первая проверка в SketchUp

### Сфера, конус, экспорт и Ruby

`create_sphere` требует `key`, `radius_mm`, `operation_id`; `center_mm` — центр
сферы. `create_cone` также требует `height_mm`; `center_mm` — центр основания,
высота идёт вдоль положительной `axis` (`X`, `Y`, `Z`, по умолчанию `Z`).
Радиус и высота положительные. `segments` принимает 12, 16, 24, 32, 48, 64, 96
или 128; по умолчанию 32. Формы создаются сетками со сглаженными гранями.
Повторная сборка по ключу требует `replace:true` и сохраняет размещение.
В JSON для `build_assembly` используются `type: sphere|cone`, `center`, `radius`,
`segments`, для конуса — `length` и `axis`; длины в миллиметрах.

`export_scene` принимает абсолютный `file_path` и `operation_id`. Формат
выбирается по расширению `.skp`, `.obj`, `.dae`, `.stl`, `.png`, `.jpg`, `.jpeg`.
Каталог должен существовать и входить в automation folders. SKP сохраняется
как копия; активный путь проекта не меняется. OBJ/STL используют миллиметры,
Z направлен вверх. Доступность экспортёра зависит от установленного SketchUp.
OBJ/DAE могут создавать сопутствующие материалы и текстуры рядом с файлом.
Для OBJ/DAE/STL можно передать `paths: [[id1], [id2]]` — экспортируются только
явно указанные корневые группы/компоненты. Выделение пользователя восстанавливается
даже при ошибке экспортёра. Для вложенного объекта доступен `export_component`
в SKP; выборочный экспорт изображения или модели SKP через `paths` отклоняется.
В DAE опция `render_compatible:true` отключает текстуры и сохранение экземпляров:
этот вариант подходит для нашего технического рендера по цветам материалов.
Для изображений доступны `width`, `height` (64–16000), `compression` (0–1)
и `transparent` (только PNG); по умолчанию 1920 × 1080, сглаживание включено.
Экспорт возвращает путь, формат и размер файла. Ошибка экспортёра может оставить
частично записанные файлы; результат отражается в журнале операций.

`eval_ruby` принимает `code` (до 100000 символов), `operation_id` и необязательный
`transaction`. По умолчанию `managed`: bridge оборачивает изменения геометрии
в одну операцию Undo. В этом режиме код не должен сам запускать/завершать
операции SketchUp. `script_owned` предназначен для кода со своими транзакциями.
Результат последнего выражения возвращается как JSON, а прочие Ruby-объекты —
как текстовое представление; также возвращается класс результата и SHA256 кода.
`puts`, `print` и `warn` возвращаются в полях `stdout` и `stderr`; при ошибке
собранный вывод включается в сообщение и журнал. Исходные Ruby-потоки восстанавливаются.
Пример: `code: "{answer: 6 * 7}"` возвращает `result: {"answer": 42}`.
Это полноценный Ruby внутри SketchUp: ограничения automation folders не являются
песочницей для кода. Файловые и системные эффекты не откатываются через Undo.
После ошибки статус — `failed_possible_partial_changes`; повтор того же ID
не запускает код снова. Для намеренного нового запуска нужен новый ID.

Изменения версии 0.3.0 проверены автоматическими тестами и сборкой RBZ;
нативную проверку новой версии нужно выполнить в открытом SketchUp.
Она также проверяет выборочный DAE/OBJ/STL, PNG/JPEG и вывод Ruby; файлы
пишутся в `artifacts/native-smoke/cache/`. После запуска можно проверить связку:

```sh
python3 scripts/render_artifacts.py artifacts/native-smoke/cache/round-primitives.dae
```

Рендер понимает единицы COLLADA, X/Y/Z_UP, вложенные трансформации и локальные
`instance_node`. Текстуры требуют нативного вида SketchUp либо повторного
экспорта с `render_compatible:true`.

### Проверка базовых команд

Открой пустую тестовую модель, запусти bridge и попроси подключённого помощника:

> Прочитай текущую модель SketchUp. Создай коробку «MCP test» размером
> 600 × 400 × 800 мм в точке 0, 0, 0. Покажи текущий вид.

Проверь размеры средствами SketchUp. Затем:

> Прочитай ID коробки «MCP test» и перемести её на 1000 мм по X.

Нажми Undo — коробка должна вернуться на место. Повтори Undo — коробка должна
исчезнуть. Для проверки изменения размеров создай её снова и попроси изменить
габариты на 600 × 400 × 1000 мм. Вращение, вложенные контексты, назначение
материалов и работу снимка также проверь на тестовой модели перед рабочим файлом.

## Диагностика

- **Bridge unavailable / stopped or busy:** SketchUp должен быть открыт, bridge
  запущен. Закрой модальные окна и дождись окончания длительной операции.
- **Active model or editing context changed:** между отправкой и исполнением
  запроса изменилась модель или открытая группа. Прочитай модель заново.
- **Entity no longer exists:** перечитай список объектов; persistent ID устарел.
- **Open the entity parent editing context first:** открой родительскую группу.
- **Request timed out:** по умолчанию запрос ждёт максимум 120 секунд. Неисполненный запрос
  удаляется. Если выполнение уже началось, оно могло завершиться: проверь `get_operation_status` и используй тот же `operation_id`. Старые
  команды без этого аргумента требуют ручной проверки перед повтором.
- **Another SketchUp instance:** останови bridge в другом окне/процессе SketchUp.
  Один каталог обмена обслуживает один процесс SketchUp.
- **Расширение не загружается:** это собственное неподписанное `.rbz`.
  Проверь политику загрузки расширений в Extension Manager и разреши загрузку
  этого расширения, если SketchUp её блокирует.

Каталог обмена по умолчанию: `~/.sketch-up-mcp` на Mac и
`%USERPROFILE%\.sketch-up-mcp` на Windows. Пункт **Bridge status** показывает
точный путь. Если домашние каталоги Python и SketchUp различаются, передай
серверу `--bridge-dir` с путём из Bridge status. Для отдельного каталога обмена
расширению можно задать `SKETCHUP_MCP_BRIDGE_DIR` в окружении перед запуском
SketchUp, а серверу тот же каталог через `--bridge-dir`.

Bridge проверяет срок действия запросов, сессию, активную модель и контекст
редактирования перед выполнением. Вызовы Ruby API выполняются через UI-таймер
в основном потоке SketchUp. Старые ответы удаляются автоматически через минуту.
MCP-сервер обрабатывает команды последовательно; отмена уже начатой команды
через протокол пока не реализована.

## Разработка и статус проверки

```sh
python3 -m unittest discover -s tests -v
ruby tests/test_automation.rb
ruby -c tests/sketchup_smoke.rb
ruby -c extension/sketch_up_mcp/bridge.rb
python3 build.py
```

На Windows вместо `python3` используй `python`. Ruby для сборки `.rbz` не нужен:
расширение исполняется встроенным Ruby SketchUp.

Автотесты проверяют stdio/MCP, схемы аргументов и вложенные batches,
обмен файлами, истечение запросов, сессию/контекст, commit/abort, журнал повторов,
параметрические панели, повёрнутые мировые трансформации, SAT и файловые границы.
Они не заменяют работу нативного SketchUp API.

После активации для проверки на настоящем SketchUp можно выполнить:

```ruby
load '/Users/st/projects/SketchUp-MCP/tests/sketchup_smoke.rb'
```

Этот тест создаёт временные детали, проверяет круги, отверстия, вложенные копии,
размеры, пересечения и сцены, затем отменяет всю тестовую операцию.
Живой тест версии 0.2.0 прошёл 11 октября 2026 в SketchUp 26.2.242 на macOS; исправленный
bridge установлен и активирован. Проверены нативные детали и размеры, столкновения
коробок и движение, независимые вложенные копии, круги и отверстия, параметрический
шкаф, сцены и варианты видимости. Дополнительно собраны все пять моделей постирочной:
ряд 1726 мм помещается в 1750 × 735 × 2750 мм; работают камера и размерная линия.
Тестовая операция отменена, исходные объекты сохранены. Отчёт:
`dist/native-smoke-result.json`. Windows пока не проверен.
